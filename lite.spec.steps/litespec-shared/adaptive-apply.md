# Execute adaptive steps

The parent owns status, integration and records. If the effective worker model matches the principal and isolation adds no value, or a trivial edit costs less than its handoff, execute directly and record it.

Before starting a pending step, use its current evidence and the [planning scale](adaptive-plan.md) to confirm or fill in its level. Replace legacy labels and preserve focused review. After a hard decision, record the contract and split or reclassify pending implementation before continuing.

For authorized steps with satisfied prerequisites, run `hard` in the parent session. For `easy` and `medium`, dispatch the matching `litespec-easy` or `litespec-medium` profile in Codex or Claude Code. Other Adaptive clients use `litespec-executor` for both.

Record the owner and attempt in the continuation note before dispatch. Invoke the selected profile once in a fresh context. Send the step path, the installed [executor instructions](executor.md), and only shared constraints or acceptance details missing from the step. Save the native handle if available. Wait for a result or blocker through native notification/wait and avoid polling, duplicate work and transcripts.

For a diagnosed in-scope defect, record and allow one correction across sessions, preferably with the same worker. A changed premise goes to the principal for revision. After interruption use Apply's active-step recovery before further edits. If delegation is unavailable and no worker is running, report once and continue directly within authorization and user budget. Never infer actual model use from a profile.

When implementation ends, before verification, record `Executed: executor | principal | executor-then-principal; corrections: <n>`. Use `principal` for direct execution and `executor-then-principal` when the parent finishes partial worker output. Keep that line when replacing continuation details with acceptance evidence.
